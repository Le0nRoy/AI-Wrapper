# Tortuga from any project

Use the existing Tortuga runner for GitHub research, implementation and review. Hermes/Claude/Codex/OpenCode are conversational clients, not competing dispatchers. Works from any directory with an explicit target, or from a GitHub checkout using its origin. Arbitrary non-Git local-folder execution is not provided.

## Prerequisites
- Tortuga checkout: `$TORTUGA_HOME`, default `/Data/Everything/ProgrammingWorkspace/Tortuga-Infra/Tortuga-AI`.
- Running bridge/webhook and GitHub App installed on the target repository.
- Existing `make get-github-token REPO=OWNER/REPO`, `gh`, Git and Python 3. No persistent gh login required.
- A connected project's own verification config: default `make test-all`/FULL_TEST_TARGET, or verify.mode=gha with explicit VERIFY_JOBS. Never silently impose Tortuga's tests on another repo. Inspect effective configuration, the actual workflow and the runner's secret/reporting rules before proposing a new test entry point or declaring an existing job blocked. Prefer the owner's selected existing verification surface; accepting its documented limitations does not authorize repairing its workflow, adding a Makefile/job, or weakening required task regressions. Use the connected-project verification preflight in [references/umbrella-workflow.md](references/umbrella-workflow.md).

## Commands
Use the terminal/shell tool. Prefix below with `python3 <this-skill-directory>/scripts/gh.py`; on the host the stable path is `python3 ~/.agents/skills/tortuga/scripts/gh.py`. Use the native client copy inside a sandbox. The helper captures the existing App-token command internally and passes GH_TOKEN only to gh; it neither changes Git remotes nor stores credentials. The Tortuga checkout and its existing token issuer must be accessible: skill installation does not grant sandbox access to infrastructure or private keys. If access is blocked, use the authorized host-side Hermes session; do not weaken sandbox mounts or copy root credentials.

```text
--repo OWNER/REPO repo
--repo OWNER/REPO issue list --limit 20
--repo OWNER/REPO issue view NUMBER --comments
--repo OWNER/REPO pr view NUMBER --comments
--repo OWNER/REPO pr checks NUMBER
--repo OWNER/REPO run list --limit 10
```

For automation, prefer explicit JSON fields, for example `issue view NUMBER --json number,title,body,state,labels,comments,closedByPullRequestsReferences,url`. Treat empty stdout from a formatted `--comments` read as inconclusive even when exit status is zero; retry with `--json` before deciding that an Issue or its comments are absent.

For loop monitoring, use `pr view NUMBER --json state,isDraft,mergeStateStatus,headRefOid,headRefName,labels,statusCheckRollup,reviews,comments,url`. Compare each `reviews[].commit.oid` with `headRefOid` before accepting its `AGENT_LOOP_META`; this gets commit-scoped review evidence through the helper's supported `pr` path without separate API authentication.

Omit leading `--repo` only when the current Git origin is the intended target. In a non-Git directory it is mandatory. Show the resolved target before the first write. Never fall back to Tortuga's own source repository.

Prefer numeric selectors. URL selectors must name the same github.com repository; the helper rejects others before requesting a token. Override subprocess deadlines with `TORTUGA_GIT_TIMEOUT` (default 10s) and `TORTUGA_TOKEN_TIMEOUT` (default 45s).

## Authorized task actions
Treat every GitHub mutation as a separate external write. Require explicit, action-specific approval before creating, editing, commenting on, closing, reopening, transferring, labeling, merging, or deleting any Issue or PR, or before pushing/publishing a branch. A capability question such as “can we create issues?”, a recommendation, broad task context, permission to edit code, or approval of a plan is not authorization to perform the write. For a batch, state the repository and exact mutation classes covered, then execute only that scope. If the requested mutation fails and a workaround changes semantics—such as recreating an Issue and closing the original—ask again before using the workaround.

Recheck the latest owner instruction before continuing an earlier batch authorization. A later planning-only, read-only, stop or do-not-edit instruction suspends conflicting writes and dispatch, including already-approved child merges and next-child research. Reconcile only through permitted reads and return the requested plan or status; do not treat standing automatic-continuation rules as permission to override the restriction. Resume mutations only when a later instruction authorizes them.

Read requirements and current labels/state before an authorized write:

```text
--repo OWNER/REPO issue create --title TITLE --body BODY
--repo OWNER/REPO issue edit NUMBER --add-label agent:research
--repo OWNER/REPO issue edit NUMBER --add-label agent:implement
--repo OWNER/REPO pr edit NUMBER --add-label agent:review
--repo OWNER/REPO issue comment NUMBER --body ANSWER
--repo OWNER/REPO pr comment NUMBER --body ANSWER
```

After a write, read back the exact Issue/PR. A visible label proves GitHub state, not delivery or runner startup. Verify actual webhook/run admission in bridge evidence before claiming execution. Do not remove/re-add a label blindly: it can duplicate work. `agent:review` targets PRs, not plain issues. Add `agent:loop` only for an actual active implement/review run and after explicit permission; verify loop activation. When restarting an abandoned coordinator, treat an already-present loop label as inconclusive: adding the same label may emit no event. Inspect the new run's coordinator evidence before reporting the implement/review loop active; distinguish admitted implementation from verified loop activation. Posting answers alone does not resume an implementation loop: use the authorized trigger and verify admission. Provider-limit recovery is different: keep monitoring and let Tortuga's built-in canary resume already-authorized work under the standing policy below; do not require another owner approval.

## Status and controls
- GitHub: linked draft PR, comments, current head and its checks are the owner-visible results. Earlier green CI does not certify a later head.
- Existing admin read endpoints: GET /admin/runs, /admin/runs/{run_id}, /admin/queue; require X-Admin-Token from local Tortuga configuration. Keep credentials inside a process, never print/source all .env into chat or send them to worker agents.
- Treat a run as admitted only when bridge evidence shows dispatch acceptance. Normally use its queued/running admin record. Review dispatch can wait for CI before its runner container or `/admin/runs` record is visible; in that phase, a bridge `waiting for CI checks` log plus the PR trigger label proves admission.
- Poll boundedly and report only state transitions. During long batches, use one background watcher with completion notification instead of repeated manual sleeps or a second task database. Also deliver changed terminal-attempt and provider-recovery records while the watcher remains alive, using bounded output heartbeats or transition notifications; completion-only delivery can hide abandoned work until a long observer budget expires. Monitor loops by repository plus PR number, current head, labels, reviews, and head checks; branch names and issue numbers can collide across repositories, and a watcher keyed only to the issue run or implement branch can settle before the review run is registered. Parse the current-head review signal instead of treating an increased review count as completion: `NEEDS_CHANGES` without owner questions normally hands off to automatic correction, so reconcile its successor and keep observing rather than redispatching.
- Treat a watcher as notification transport, never as the owner of workflow progress. On every conversation resumption, status request, completion notice, or missing-process result, immediately reconcile the exact Issue/PR and bridge state, then continue the authorized batch without waiting for the user; a watcher can exit or disappear after remote work has already become mergeable. If green CI resolves the review's sole factual question, post verified evidence within comment authority and request final review rather than waiting for another owner instruction or dispatching unnecessary implementation. Record that review request's comment ID, dispatch boundary and head; require a later review that explicitly resolves the question, because an earlier same-head APPROVED signal can remain visible while the new request is being admitted. Do not translate the bot's generic “add implement + loop” footer into an implementation requirement when only verification evidence changed. Advance through the authorized child merge and next-child admission before reporting progress, unless a real gate remains.
- When one Python watcher hands off to another, execute the child with `sys.executable`, not a hard-coded `python3` path; the latter can combine a runtime with incompatible standard-library extension modules.
- Give the outer background job enough runtime for both issue and PR phases; an `exec` handoff inherits the outer deadline, so a correct inner watcher can still be killed before CI or review finishes. Use completion notification and `persist_on_release=true`, but still reconcile remote state after any notification gap.
- When reporting a monitoring gap, distinguish an intentional stop from lost watcher continuity. State the last verified remote transition, reconcile immediately, and resume the authorized workflow before replying. Treat repeated observation errors as lost coverage, not healthy monitoring: isolate the failing read and repair the observer while checking remote state directly. Emit the failed stage, exception class and exit code without credentials; repeatedly refreshing authentication cannot repair an unrelated parsing or bridge-read failure. Keep heartbeat payloads compact: report changed head/check/run state, structured review verdict and a comment identifier or short excerpt rather than replaying full welcome comments and reviews. After switching targets, verify the replacement observer works, then stop only the exact obsolete read-only observer; do not confuse its intentional termination or delayed heartbeat with failure of the active Tortuga job.
- Store multi-session observer scripts and the compact batch cursor in persistent local state, not age-pruned scratch or cache directories. Use `${XDG_STATE_HOME:-$HOME/.local/state}/tortuga-observers/` or an existing durable task workspace; `persist_on_release=true` preserves a process, not its script or handoff files. Record current child, current PR, last verified head/gate, next child, integration PR, preserved dirty files and observer location. Replace superseded phase, gate, pending-decision and next-action fields together at each handoff; adding a new contract beside stale authoritative fields leaves a contradictory recovery cursor. Before launching, verify the script exists and parses; after launching, verify the observer is alive separately from remote run admission. If the script disappears, reconcile remote work first, restore only the read-only observer and cursor, and do not redispatch a healthy task. On a status or “why did this stop?” question, rebuild the remaining sequence from live umbrella children, current Issue comments and linked PRs before answering; a compacted cursor can lag multiple completed children and superseding owner decisions. Distinguish an intentional approval gate, lost notification continuity, a terminal runner attempt and an abandoned coordinator. If GitHub exposes only `failed` or exhausted retries, inspect the run-scoped verification/log evidence and bridge queue before naming the cause or claiming recovery; those status flags do not establish provider exhaustion. Report the last verified transition, the exact remaining sequence, the evidence-backed blocker and whether anything was committed, pushed, merged or deployed. Within still-active batch authority, perform the applicable recovery or establish monitored canary waiting before ending the status turn; a diagnosis and promise to resume are not a handoff.
- Treat trigger labels as events, not durable run history: automation may consume `agent:review` or `agent:implement`, so their later absence does not prove they were never applied. Use dispatch comments/admin evidence to prove admission, and do not re-add a consumed label after a completed loop unless fresh work is authorized.
- When a review run ends and the trigger label disappears without a machine-readable loop signal, inspect the current-head review body before calling the loop stale. A `COMMENTED` review (including final integration reviews without metadata) can still contain explicit blocking findings; resolve those findings and re-enter the authorized implement loop rather than merging on the absent signal. When a PR sits in `agent:queued` while a runner container is active, inspect `docker top <runner>` / `wchan` for processes stuck in `do_signal_stop` / `T` state (`SIGTTIN`/`SIGTTOU`).
- Scope every `AGENT_LOOP_META` result to the review's commit SHA. A feature or umbrella PR is ready for human acceptance or merge ONLY when BOTH (1) all current-head CI checks are green AND (2) a current-head review comment containing `<!-- AGENT_LOOP_META {"signal": "APPROVED", ...} -->` is present. Ignore an approval, rejection or open question attached to an older head and wait for a current-head review; otherwise a stale question can stop a repaired loop or a stale approval can certify new code. An `APPROVED` signal with open questions or failed required checks is not merge-ready. Classify skipped checks separately from passed checks: inspect the exact diff and workflow path filter before accepting a skip as inapplicable, and never reuse a prerequisite's successful E2E result as proof that the current child ran E2E. Require actual E2E passage when the approved task or applicable workflow requires it; report a justified path-filter skip explicitly rather than calling every check green. Verify infrastructure-failure claims from failed job logs; code approval does not waive the CI gate.
- For an authorized CI rerun that fails authentication or authorization, refresh the 1-hour repository-scoped GitHub App token (`gh.py token`) and retry once before proposing an empty-commit CI trigger fallback. Distinguish expiry from persistent permission denial; never broaden credentials implicitly. If direct rerun remains denied, request explicit approval before substituting an empty commit: it reruns all applicable workflows, changes the head, and requires fresh current-head review even when the tree is unchanged. Reconcile remote state before creating or pushing the fallback so concurrent automation cannot cause duplicate retriggers. Follow the CI-retrigger recipe in the umbrella workflow reference.
- Invalidate a settled approval when a later authorized correction request or revised owner contract reopens work, even if the head SHA has not changed yet. Track that pending correction through dispatch and require a review covering its resolution; matching the current SHA alone can otherwise reuse the approval that the correction explicitly superseded. If review is already running, post the authorized correction on the exact PR and record its unmet acceptance criterion before triggering anything else. Let an admitted review and its automatic correction successor consume the request; reconcile the resulting diff, new head and fresh checks before deciding whether a separate implementation trigger is needed. Do not run competing implementation merely because the current review began before the owner's decision.
- Treat prose-only “improvement opportunities” as non-blocking when the current-head `AGENT_LOOP_META` says `APPROVED` with no issues or open questions. Preserve them as follow-up candidates; do not turn optional review commentary into an invented merge gate.
- When a loop finishes with open questions, classify each against the approved acceptance criteria before escalating. Validate dependency-removal findings through the pinned tools' transitive requirements and runtime imports, not only imports in the repository: a package unused by project code can still be required by a linter. For hash-locked Python installs, inspect the exact release wheel's `Requires-Dist` metadata and relevant imports, verify its published digest, and retain required transitive pins/hashes. Return a disproved finding with that evidence for corrected review of the unchanged head; do not dispatch removal work, create a speculative follow-up, or ask the owner to decide a factual dependency question. Resolve a required failing test gate from verified code, CI and approved intent; a reviewer's deferral or follow-up option does not waive it. Implement a repair only within the current mutation and behavior-change authority. Under retry-only authorization or a behavior-preserving refactor, a production lifecycle, readiness-timeout, resource or harness change remains a separate decision even when it could make required CI pass. Keep the gate blocked rather than dispatching unchanged-code correction cycles or treating the gate itself as repair authorization. Post answers only when PR comments were authorized, then re-enter the authorized implement loop and verify both dispatch and later completion. Posting an answer alone does not resume the loop.
- Remote automation may advance the branch while the local checkout and its remote-tracking ref remain stale. Before validating, repinning a dependency, or reporting exact SHAs, fetch the affected repository, compare the PR head with local HEAD, and fast-forward a clean checkout; otherwise local success can certify an obsolete revision.
- For dependent submodule and superproject PRs, finish the submodule loop first. If its head changes, update and verify the parent gitlink before starting or accepting the parent review; parallel approval can certify a stale dependency pointer. After the dependency merges, fetch its default branch and repin the parent to the actual merge commit before the parent merges: squash/rebase creates a new canonical SHA even when the tree is identical. Push that repin and require fresh parent checks at the new head.
- Diagnose terminal implementation failures by stage: inspect `suite_result`, the configured verification target, `push_result`, remote head, PR existence, and the exact publication error separately. A passed unit-only target is not a full-suite pass, and a pushed branch is not a PR. In Tortuga, report `make test-via-image` as unit-only; require separate actual E2E evidence when applicable. Inspect the invoked target rather than copying an automated “full suite” summary, and keep reporting truth separate from authority to edit behavior-preserved output. A retry reporting `completed`, `nothing_to_push`, or skipped verification does not finish previously published work: compare the existing remote branch against its intended base and require the actual PR and head-scoped verification. Do not manufacture a code change merely to make the runner publish; recover the already-authorized publication directly when possible. For `initial_session_failed` or an empty admin error, inspect the run-scoped verification record and runner log before classifying the failure; provider limits can terminate the agent before tests or publication. Before redispatch, inspect the existing retry queue and reconcile its intended run ID; let an admitted automatic retry own execution rather than adding duplicate labels. Watch queued retry admission without mistaking a temporarily absent run record for failure.
- On provider quota exhaustion, preserve work and keep monitoring through the wait. Use Tortuga's built-in provider pause and canary recovery; waiting for restored limits and continuing the already-authorized batch are the owner's standing default, not a new approval gate. Do not stop monitors, ask permission to wait, manually substitute reset timers, or change models, effort, providers, accounts, or global quota settings. Reconcile canary, queue, run and PR evidence, and continue automatically when limits recover; a terminal attempt or watcher timeout is not permission to abandon the batch. Renew bounded monitoring when needed without creating another scheduler or duplicate dispatch. Check the watcher's executable exit predicate before launching it: `completed_at`, `retries_exceeded`, or a failed/timed-out attempt must not terminate observation during quota recovery. Before relying on an edited observer, run a small transition self-check covering active work, exhausted retries, replacement admission, substantive `COMMENTED` final integration reviews without metadata, and owner-gate exit; syntax checks and a live PID cannot prove lifecycle correctness. Compute whether a record changed before updating the previous signature, so transition diagnostics do not become unreachable after state assignment. Follow admitted replacement runs scoped to the repository, task and dispatch boundary; exclude every earlier completed dispatch, not just the most recent run, so a repeated research or implementation watcher cannot immediately settle on old work. Reconcile canary and queue evidence before interpreting a failure or missing replacement. If the canary clears the provider but exhausted retries have abandoned the task coordinator, reconcile active runs, retry queues and existing publication before acting. Within existing comment/label authority, retrigger the abandoned task once on the unchanged approved route and verify actual readmission; no new wait/resume approval is needed. Do not retrigger while another recovery attempt owns the task. Distinguish provider recovery from task recovery: a cleared canary alone does not prove execution resumed. When the owner explicitly reports restored capacity, reconcile and resume the already-authorized abandoned task without demanding another approval; let an existing provider pause or admitted retry retain ownership. Attribute restoration to the owner report unless fresh canary evidence independently confirms it, and verify readmission before calling the task running. Investigate and report other recovery faults rather than claiming automatic resumption is guaranteed. When the exact limit message fails the deployed classifier, no provider pause/probe state exists, and the task has exhausted retries with an empty queue, report a recovery-path fault—not healthy canary waiting. Keep read-only observation alive, but do not imply that renewing its deadline repairs dispatch or detects restored provider capacity. Separate permission to wait/resume from authority to change infrastructure; obtain the latter before changing classification or deploying a repair. Follow the quota-failure recipe in the umbrella workflow reference; this standing canary-first policy supersedes older manual-delay guidance.
- When an implementation runner cannot publish, verify recoverability before promising recovery: check the recorded worktree, exact commit object, remote branch/commit, and exported patches. A verification record preserves a tested SHA, not its Git objects. With publication authority, prefer publishing the existing commits owner-side; never loosen runner credentials or push policy. If no recoverable code or admitted successor exists, report the loss plainly and restart once within existing implementation authority, carrying prior findings only as context and requiring fresh verification. Do not transfer historical test passes to reconstructed code. Follow the publication-recovery recipe in the umbrella workflow reference.
- For infrastructure operations read Tortuga's AGENTS.md, docs/workflow.md and docs/operations.md. Existing `make stop-agent` is destructive and needs exact-run authority; inspect its current arguments first. Do not invent a generic pause/resume API.
- Keep queueing, quota waits and recovery in Tortuga. Do not create native Hermes Kanban jobs, Workflows graphs or a second task-state database.
- Do not deploy, merge, grant App access, change quotas/models or launch unrelated tasks as a side effect of status checks.

## Umbrellas and sequential sub-issues
Establish a milestone umbrella issue AND the umbrella integration branch (`agent/feature-<umbrella_num>`) plus draft PR at milestone kickoff (not at the end) before dispatching any Tortuga job for milestone work; this is a mandatory gate, not optional tracking overhead. During planning, enumerate the milestone issues, inspect their native parent links, and search for an existing umbrella rather than assuming the milestone itself provides one. If absent, obtain explicit authorization to create the umbrella, its integration branch/draft PR, and attach its children; planning-only permission does not authorize these writes or any job.

Preserve existing parent chains when grouping issues under the umbrella. If direct attachment would replace a parent, present preservation versus flattening as selectable choices before changing links; parent relationships control integration-branch routing. With preservation selected, attach only the roots and verify every original milestone issue is reachable recursively. Report direct-child and nested-descendant counts separately.

Before finalizing milestone scope, inspect open issues without a milestone and in Backlog for duplicate or overlapping work. If no explicit Backlog milestone or board is identified, treat Backlog as issues without a milestone rather than blocking on a board URL. Separate strong overlaps, related work, and verification risks; propose reuse, dependency coordination, or inclusion without silently moving issues or expanding scope. Once the owner excludes candidates, record that exclusion in the execution contract and do not turn related tooling into prerequisites. Check historical findings against current code before treating them as outstanding defects. Read [references/umbrella-workflow.md](references/umbrella-workflow.md) for the discovery and hierarchy API recipe.

Process children in the umbrella's stated order. Before each action, read the child's state, labels, comments and linked PRs; skip already-closed work. Welcome text, dispatch notices, reactions, prior labels and automated scope/decomposition instructions do not count as research: select the substantive findings comment by content, not merely the newest comment, and require scope plus open-question disposition. When a research run completes without that report, inspect its bounded run log and publication evidence before advancing; successful process exit can conceal an unpublished result or an abandoned background task. Reconcile active successors and the queue, recover an existing report when available, or retry once within existing research authority using bounded foreground probes and explicit report delivery. Never dispatch implementation from the completion flag alone. Follow the unpublished-research recovery recipe in the umbrella workflow reference.

For agent installation/compatibility work, establish maintained-agent scope from a current authoritative registry or interface before accepting a coverage matrix; historical architecture notes and package-upgrade commands do not establish the complete supported set or current sandbox mounts. Verify the supported configuration schema and distinguish declaration, installation, discovery and session loading; an existing writer or newly created directory proves neither consumption nor usable functionality. Honor source-inspection exclusions across submodules and installed runtime copies. If authoritative evidence is excluded, request narrow read-only access or an explicit scope decision rather than guessing unsupported agents, duplicating installers, or silently deferring required functionality. Follow the installation/discovery research recipe in [references/umbrella-workflow.md](references/umbrella-workflow.md).

Resolve implementation-detail questions from code, docs and existing architecture, using applicable industry standards and authoritative language/tool documentation as weak supporting evidence rather than automatic authority. Existing code establishes current behavior, not necessarily good design. Cite the relevant standard/version, explain applicability and concrete trade-offs, and seek approval when adopting it changes functionality, scope, or a material architectural choice. Post the resolution only when Issue comments were explicitly authorized; otherwise present the proposed comment for approval. Keep approval questions laconic: name the affected task, decision, concrete risk or benefit, and selectable answers with the recommendation first. When the owner requests alternatives before deciding, complete focused feasibility research before asking again; include an explicit overengineering assessment in the question itself, naming the extra machinery, maintenance/test cost, and behavior at risk rather than merely labeling an option complex. Distinguish failure of the current mechanism from proof that every alternative is impossible. Verify material runtime claims with a small native probe and positive/negative controls where available; a runner limitation is not evidence that the owner's environment lacks the runtime. Enumerate the full exception boundary, including transitive callback/support functions, rather than presenting a few entrypoints as the entire exception. Keep proposed body changes and behavioral regressions unapproved until the owner selects them. When asked to repeat questions, reopen the selectable question form with the unresolved choices and concrete proposals, not just a prose recap. Preserve answered choices and ask only what remains unresolved. Do not configure an answer timeout for this owner; if the interaction surface imposes one, leave the decision unresolved and never treat expiry as consent. Treat a free-text correction as the actual decision, not as acceptance of the nearest offered option; record its usability constraint and leave any unspecified security mechanism unresolved. If the owner chooses removal instead of the offered access controls, replace the obsolete options in the worker contract before dispatch. Enumerate the feature-specific mounts, environment passthrough, trust/writability classifiers, docs and tests to remove, while explicitly preserving shared capabilities. Removing wrapper support does not authorize uninstalling software or deleting installed user data. Inspect bundled installers before declaring removal complete: an installer can still provision the retired feature after its runtime mounts disappear. If that installer also supplies a shared tool, ask one selectable scope question covering retention, splitting or complete source removal; do not silently remove the shared installation feature or invent a replacement. Carry the selected deletion and reference cleanup into the worker contract, and verify the resulting diff and absence assertions without running deployment cleanup. Avoid best-practice slogans without evidence.

When a report marks `SCOPE: SINGLE_TASK` but lists adjacent defects or follow-up candidates, do not silently expand or decompose the current child. Record the candidates for the batch handoff and continue unless one invalidates the stated acceptance criteria or creates an unresolved security boundary; this prevents opportunistic audits from stalling the authorized umbrella.

Before proposing decomposition from an older report, compare its inspected SHA and policy assumptions with the current integration head. When intervening children changed shared helpers or the owner revised scope, dispatch a research-only refresh within existing authority before asking for split approval; otherwise the proposed children can duplicate completed work or revive rejected mechanisms. Carry the verified base SHA, canonical sibling ownership, deferred work and unresolved design gates into that refresh. Do not create children or implement while refreshing. If a focused correction still mixes unsupported mechanism claims with otherwise separable work packages, propose a bounded split for owner approval and move feasibility research into the relevant children instead of repeatedly rerunning the whole audit. State which claims remain unverified; approval of the split must not turn them into implementation requirements.

If research returns `SCOPE: NEEDS_DECOMPOSITION`, do not add `agent:implement` until an explicit owner-approved scope split resolves that gate. Before proposing nested children, trace integration-branch routing and dependency order: nesting an immediate prerequisite together with a final reconciliation task can strand prerequisite changes on a branch whose completion depends on later siblings. Prefer proposing a narrowed prerequisite issue plus a final-reconciliation sibling under the existing umbrella when that avoids the cycle. Obtain explicit approval for creation, scope edits, and parent links; record the resolution and verify the resulting hierarchy before implementation. A newly created sibling still needs its own research. For nested decomposition, explain the proposed split and ask for explicit approval before adding `agent:decompose`, because that label creates Issues. Prefer Tortuga's built-in decomposition over manually creating approved children; the owner expects the existing workflow to own issue creation. Before triggering it, publish one authoritative approved package list with the exact count, parent/milestone, exclusions and unresolved policy gates, explicitly superseding older report checklists. Approval to create packages and research them does not select the mechanisms or defaults proposed inside them. Read back the trigger and verify a matching `decompose` run; after completion, enumerate the actual children and verify their scopes, count, parent links and milestone before splicing them into the current child's position. Inspect literal commands, variable names and controls in each generated body as well as its title: shell expansion during publication can erase identifiers while leaving plausible prose. Within authorized issue-edit scope, repair serialization damage from the approved specification and read back the exact body; do not treat generated omissions or stricter recommendations as owner-approved scope changes. Do not manually duplicate children while the decomposer is admitted. Each created child still needs its own research gate; parent research and a generated body are context, not a child-level findings report. Finish all nested children and verify the decomposed parent is closed or explicitly resolved before advancing in the original umbrella order.

Before nested-child implementation, resolve its intended PR base through the native parent chain and read the remote refs for every required integration branch. Distinguish the revision inspected by research, the revision supplying approved lint policy, and the actual native implementation base; sibling integration branches do not inherit each other's unmerged changes. Record an acyclic availability sequence: finish the independent prerequisite on its native branch, merge it into the shared ancestor, then integrate that ancestor into the dependent branch with fresh verification before final reconciliation. Do not credit a parent's acceptance criterion with sibling work until that code is present and verified on its actual integration head. Do not assume research dispatch or parent creation published required branches; a pushed child cannot open a PR against an absent base. If a prerequisite ref is missing, resolve its creation within explicit branch-publication authority before dispatch; do not bypass routing by targeting the default branch.

When research is ready and the batch authorization includes looping, add `agent:implement`, read it back, and verify bridge admission. Once the implementation run is active, add `agent:loop`, read it back, and verify actual loop activation; a loop-label event before an active run can be ignored. Do not start the next child until the current PR is merged/closed and the child closure is visible. Never classify a loop as stale while a latest-head check is queued or running; lack of a status transition is not inactivity. A stale loop is not automatically safe to merge: when the user's runbook explicitly authorizes stale-loop merges, still inspect the latest head, CI, review requests and unresolved questions first.

Record the local checkout's initial branch and dirty files before the batch. Preserve unrelated or intentionally deferred configuration edits throughout child work. Apply and commit those edits to the integration branch only after every child is closed and only the integration PR remains. Before committing a default-setting change, trace its schema fallback, generated/reference docs, and hard-coded test expectations; a YAML-only edit can leave startup fallbacks and CI inconsistent.

Classify integration merge gates by the PR's actual base and the owner's authorized scope, not by the word “integration” in its title. When the owner authorizes milestone implementation and nested integration merges through final acceptance, carry green reviewed children and nested integration PRs into their intended parent branches without requesting approval again or stopping after a completed sub-batch. Check `isDraft` and run `gh pr ready <num>` before `gh pr merge`. Audit that `agent:loop` attaches automatically to parent integration PRs when all sub-issues close (track Tortuga-AI `#739` / `#921`; attach manually only if webhook automation did not fire). Before each nested merge, verify its descendants are complete; an integration PR can exist while unfinished children still belong to it. Reconcile the live remaining milestone work, admit the next authorized task and renew monitoring after each merge. Update the umbrella's authoritative execution contract and durable cursor when broader authorization supersedes an earlier narrow batch; do not keep enforcing the old batch boundary. Preserve separate approval gates for new lint exceptions, functionality changes, credential sharing and unresolved material design decisions.

Reserve final acceptance for the integration PR targeting the default branch (or another explicitly named final target). Once that exact head has BOTH all current-head CI checks green AND a current-head `<!-- AGENT_LOOP_META {"signal": "APPROVED", ...} -->` review comment, stop and provide its URL, SHA, verification results, residual risks, and a self-contained manual acceptance checklist (exact revision, reproducible setup, actions, expected results, known exceptions, sign-off boundary). Do not merge into the final target or deploy without separate explicit approval. Permission to merge nested integrations does not authorize the final merge; conversely, withholding the final merge does not prohibit already-authorized nested merges.
