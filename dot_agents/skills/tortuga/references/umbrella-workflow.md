# Sequential umbrella workflow

Use this recipe when one umbrella tracks several child issues and the user authorizes the specific research, implementation, comment, label, publish, and merge mutations needed for the batch. Name the authorized mutation classes; permission to pursue the outcome alone is not write authorization.

## 1. Establish scope and protect local state

### Discover the milestone umbrella and overlapping work

1. Read the milestone metadata and enumerate its issues with `issue list --milestone NUMBER --state all --limit LIMIT --json number,title,body,state,labels,url`; reconcile the collected count with milestone metadata and paginate or raise the limit when needed.
2. Inspect native parent links for each issue and search issue titles and bodies for a milestone umbrella. A title search alone is not proof of absence. Check the hierarchy rather than relying on body checklists.
3. Enumerate open repository issues with pagination. Partition those without a milestone and those assigned to the actual Backlog milestone; exclude pull requests returned by the REST issues endpoint. Compare bodies and substantive research with milestone scope, not titles alone.
4. Report strong overlap separately from adjacent work and test risks. Recommend reuse of existing issues before proposing duplicates. Do not move, reparent, or dispatch candidates without explicit authorization.
5. If the umbrella is missing, stop at the authorization gate. An explicit request to create the umbrella and attach children authorizes organization only, not research or implementation dispatch. If existing parent links would be replaced, ask whether to preserve nesting or flatten before changing them.
6. Under organization authorization, create the umbrella in the milestone without dispatch labels, and establish the umbrella integration branch (`agent/feature-<umbrella_num>`) plus draft PR at milestone kickoff (not at the end). Preserve approved nesting by attaching only roots. Read back the umbrella, each changed parent, and preserved nested links; recursively enumerate descendants and assert that every original milestone issue is covered. Distinguish direct children from nested descendants in the result.

For endpoints not exposed by the skill helper, capture `make -s get-github-token REPO=OWNER/REPO` inside a process and pass it only through `GH_TOKEN` to native `gh api`. Do not add unsupported `api` arguments to `scripts/gh.py`. Useful REST operations:

- Read metadata: `GET /repos/OWNER/REPO/milestones/MILESTONE_NUMBER`.
- Enumerate issues: `GET /repos/OWNER/REPO/issues?state=open&per_page=100`, using `gh api --paginate --slurp`.
- Read a parent: `GET /repos/OWNER/REPO/issues/CHILD_NUMBER/parent`. Treat the specific no-parent 404 as absence, not authentication or transport failures.
- Attach a child: `POST /repos/OWNER/REPO/issues/PARENT_NUMBER/sub_issues` with JSON `sub_issue_id` set to the child's numeric REST database `id`, not its issue number, and `replace_parent: false` to protect existing links.
- Enumerate children: `GET /repos/OWNER/REPO/issues/PARENT_NUMBER/sub_issues?per_page=100`, paginated at every hierarchy level.

Keep payloads in process memory and verify set membership programmatically. Authorization to attach children does not imply authorization to replace their existing parents.

### Protect the checkout and establish execution order

1. Read the umbrella body and preserve its child order.
2. Run `git status --short --branch` in the intended checkout before any write.
3. Record pre-existing dirty files. Do not stash, reset, fold into agent work, or deploy them early.
4. Read each child's `state`, `labels`, `comments`, `closedByPullRequestsReferences`, and URL before deciding its next step.
5. After a prerequisite merges, give the next research worker the actual integration branch and verified merge SHA. Require inspection of that revision; research dispatched from the default branch can otherwise miss the prerequisite's new helpers and safety guidance.

Skip a closed child. Do not re-run research or implementation merely because the umbrella checkbox is stale.

## 2. Research gate

A child is research-ready only when comments contain a substantive report with:

- root cause or current-state evidence;
- scope disposition;
- proposed implementation and tests;
- explicit open questions with resolved/unresolved status.

Welcome text, emoji reactions, dispatch notices, removed labels, and automated “decomposition required” follow-ups are not research output. When several comments land together, select the report by its evidence, scope, tests, and question analysis rather than taking the newest comment; automation often posts a shorter instruction after the actual report.

If no report exists and the user explicitly authorized research-label writes, add `agent:research`, read the issue back, then verify a matching record in `GET /admin/runs`. Otherwise present that next action for approval. Do not remove and re-add the label while an admitted run is queued or running.

When the report lands:

1. Resolve code-level questions from repository evidence. Validate the proposed mechanism separately from the reported defect; a useful finding does not certify its suggested fix.
2. For test-isolation prerequisites, inspect live-client execution, inherited HOME/XDG/client state, command resolution, and suite side effects before running tests. Do not treat a fixed system PATH as excluding installed clients or as filesystem confinement. Require synthetic client traps/stubs and canaries for the actual resolution paths while preserving required toolchains; reserve enforcement claims for real sandbox tests.
3. Post the resolution only when Issue comments were explicitly authorized; otherwise present the proposed comment for approval.
4. Ask the user about unresolved product or architecture intent. State the child, the decision it controls, evidence, and a recommended answer.

### Recover completed research without a published report

1. Read the issue comments as JSON and select substantive findings by content. Pair them with the exact admitted run; `completed` and exit code zero prove neither report creation nor publication. Do not accept a dispatch notice as the missing deliverable.
2. Inspect a bounded, credential-safe excerpt of the recorded run log for report creation, publication failure and background-task ownership. Distinguish a recoverable report from a run that never wrote one; do not reconstruct findings from a progress announcement or transfer old test passes to a new report.
3. Reconcile matching active runs and the retry queue before writing. Leave an admitted successor in control. If a complete report survives, recover its publication within existing comment authority rather than repeating the investigation. Otherwise, with research-trigger authority and no successor, record the failure mechanism and renew research once on the unchanged approved route; verify readmission.
4. When background-task waiting prevented delivery, require focused synchronous foreground probes with explicit per-command deadlines. Reuse already verified prerequisite evidence instead of rerunning its entire suite merely to begin research. Require a substantive report even when a probe cannot run: publish the exact runtime gap or unresolved decision rather than withholding the report while a background task owns delivery.
5. Reset the observer's dispatch boundary to exclude every earlier completed attempt, update the durable cursor and verify both the replacement task and observer. Keep implementation gated on the actual report. If the same delivery failure repeats, diagnose or recover through the authorized owner-side path instead of cycling labels indefinitely; change no model, provider, timeout policy or infrastructure implicitly.

### Verify cross-shell loading and parity research

1. Record the exact integration revision, canonical public/private classification, allowed callbacks and permitted body/caller changes. Inventory source files, real callers, alias definitions, environment/setup interfaces and platform deployment exclusions before choosing a shared module. A helper previously present in every shell must not move solely into a module omitted on another supported platform.
2. Execute small native probes in synthetic HOME/XDG with controlled command resolution, not real host startup or settings. Capture stdout, stderr, helper status and shell status separately. Exercise actual bodies: help-only calls and successful module sourcing cannot detect unavailable builtins or different glob semantics. Include matching and unmatched globs, spaced arguments, failure paths, alias expansion and repeated calls. Never infer owner-host capability from the runner's installed tools.
3. Pair each incompatibility with a legitimate-operation control. For stateful helpers, seed cwd, options, environment and caller variables, then verify intended mutations and unrelated-state preservation after success and failure. For transfers, capture each argument separately so stringified logs cannot hide changed boundaries. Serialize alias and environment values with `printf '%s\n' "$value"`, not `echo`: native shells can interpret backslash escapes differently and corrupt the comparison itself. Preserve embedded newlines with structured or length-delimited records instead of truncating a value at its first newline. For concurrent pipeline stages, assert each stage's exact arguments, multiplicity and required dependencies without assuming their log writes have one total order; do not globally sort sequential command logs and hide real ordering regressions. Emit each fixture log record with one append so concurrent writers cannot interleave its bytes. If canonicalizing observed stage order, restrict it to exact adjacent pairs from the known pipeline, verify those stage records actually occur with the expected multiplicity, and retain controls rejecting lost/duplicated stages, unrelated swaps and intervening serial calls. Apply that rule to every exercised pipeline rather than repeatedly fixing one scheduling symptom. Pair a failed PTY completion with a direct callback control using the same command words, cursor position and fixture, then inspect actual buffer/input-mode state before selecting a repair. A successful callback does not prove interactive completion, and a failed PTY assertion does not by itself identify a callback defect. In supported default keymaps, send one Tab, wait for its output, then use Ctrl+L to redraw the line before matching the full expected buffer: successful completion may emit only the inserted suffix. Retain a negative fixture without the candidate so redraw cannot turn the assertion into an unconditional pass. A child-shell wrapper cannot propagate caller cwd/options; a subshell using the same incompatible interpreter cannot supply another shell's builtins.
4. Evaluate the smallest body-preserving loading or interpreter boundary per helper. Keep compatible stateful helpers in-process; test explicit interpreter execution for nonportable command/output helpers when it preserves the approved contract. Verify quoting, status, output, environment and intended aliases rather than assuming equivalence. Do not globally change shell options, add unapproved compatibility callbacks, duplicate bodies or build dynamic extraction/eval machinery to make a matrix appear green. Escalate only a demonstrated conflict that changes scope, behavior or an approved exception.
5. Test registration repairs outside the target runtime, inside a valid synthetic runtime, and with failed runtime discovery. Moving a hook guard outside initialization must not register a pane hook without a valid pane. Preserve third-party hook order/content and unrelated PATH entries; fix repository-owned membership rather than globally deduplicating vendor state. Keep private callback bodies unchanged when only loading/registration edits are approved.
6. Prove interaction claims in isolated PTYs: command discovery, actual completion entrypoints, Ctrl+D on empty/nonempty input and repeated startup. Separate helper definition/alias absence from unrelated executables with the same name. Record simulated missing-module layouts separately from native platform evidence. Return unsupported portability claims with measured counterexamples; when those establish an in-scope correction, write one authoritative implementation handoff instead of requesting repeated broad research or a policy decision about a factual shell difference.

### Verify terminal-multiplexer preservation and prefill safety

1. Record the exact integrated revision and read the configuration, startup script, shell-history callbacks, restore-hook declaration and command aliases before accepting a preservation report. Trace which interpreter consumes each hook: a plugin may evaluate a shell command rather than send it through the tmux command parser. Inspect alias expansion on automated cleanup calls as well as interactive commands; an interactive confirmation alias can break a scripted command with additional arguments. Preserve the interactive safeguard when proposing a narrowly scoped automation correction. Record full plugin commit IDs and actual runtime versions; short hashes and worker summaries are leads, not independently verified provenance.
2. Create a fresh test-owned HOME, XDG state and socket tree under managed scratch. Sanitize inherited TMUX/TMUX_PANE and route every tmux operation explicitly, for example `tmux -S "$test_socket" -f /dev/null new-session -d -s probe ...`. Before the first native call, create and validate the parent of an explicit `-S` socket path inside the fresh fixture: tmux does not create arbitrary missing parents for that path. Require the test-owned socket directory's expected ownership, private mode and non-symlink identity; classify setup failure before attributing it to production behavior. Read scripts for PATH resets and nested plugin calls before relying on command traps. For a boot script that resolves tmux after replacing PATH, a leading fake executable does not contain its calls; establish a fresh TMUX_TMPDIR and prove the actual selected socket and subprocess routing. Do not inspect the owner's default socket to prove isolation: it may legitimately exist and remains outside scope. Before cleanup, verify the socket is inside the fixture and its server PID matches the recorded test server; terminate only that exact server. Never use a default-socket kill or process-name-wide cleanup.
3. Establish prefill failure controls before recommending a fix. Cover normal text, named key strings such as Enter, multiline input both with and without a final newline, spaces/tabs, CR, ESC, DEL, other relevant C0 controls and NUL handling. `wc -l` counts newline bytes rather than logical lines, and removing ASCII spaces does not reject all whitespace. `send-keys -l` prevents named-key interpretation but still delivers control bytes to Readline/ZLE. A real isolated Bash probe demonstrated that literal text ending in Ctrl+O (`0x0f`, operate-and-get-next) executes without an explicit Enter argument. Do not present LF/CR rejection plus literal mode alone as a complete safety boundary, or silently strip controls into a different command.
4. Prove execution and non-execution with test-owned side effects, not captured text alone. Start a clean interactive shell in the private pane and wait for readiness. Send a harmless command that would create a unique fixture token; require the token to remain absent while accepted text is visible in the input buffer, then send an explicit test Enter and require token creation. Pair hostile payloads with successful ordinary punctuation, quoting and Unicode controls. Test the actual supported Bash/Zsh input modes and disclose assumptions about trusted keymaps; arbitrary user bindings can assign actions to printable characters. A fake tmux argument log proves forwarding, not line-editor safety. Initialize a PTY fixture's native hook state in the same order as real startup before sourcing the module. In bare `zsh -f`, an unset `precmd_functions` differs from an initialized empty array: an index-based membership guard can leave the logger unregistered. Require a hook-execution canary, not shell exit zero alone, and model actual interactive history events instead of assuming noninteractive `print -s` plus `fc` has the same current-event semantics. Validate membership probes with unset, empty, singleton-match, multi-hook-match and multi-hook-no-match arrays. In native Zsh, use `${precmd_functions[(Ie)_tmux_log_last_cmd]}` compared with zero for exact membership: `${#${(M)precmd_functions:#_tmux_log_last_cmd}} > 0` returned false for a tested multi-hook array despite passing the singleton control. Correct the fixture rather than production registration/history semantics. Inspect full logical input lines with `tmux capture-pane -p -J` when commands wrap; a physical last-row suffix is not proof that prefill is absent. Keep the no-execution sentinel and explicit-Enter positive control independent of text rendering. Clean up the verified private server even when an assertion fails.
5. Verify real persistence separately from branch mocks: create multiple sessions/windows/panes with known geometry and cwd, populate history and last-command fixtures, invoke the actual declared save implementation, mutate or destroy only the private server, then restore through its required execution context. Some restore scripts need TMUX set by `tmux run-shell`; direct invocation from an unrelated shell is not equivalent. Compare before/after inventories, geometry, cwd, history, prefill state and file modes. Separate semantic identity from recreated runtime identifiers: restoring a server can legitimately change pane IDs while preserving session/window/pane positions. Inspect the actual runtime layout format before normalizing it; legacy layout strings and JSON layouts need separate controls. Normalize only legacy checksums and ephemeral pane identifiers, including JSON `I` values; retain pane index `i`, hierarchy, orientation, ordering, dimensions, coordinates, active flags and cwd. Require negative controls for changed geometry, active state, cwd and lost/duplicated panes in every supported representation; a legacy-only normalizer cannot certify a native JSON run. Exercise recording from inactive panes in different windows and sessions while another pane remains selected. Compare the callback's resolved pane with `TMUX_PANE`, and require both the correct pane's state update and unchanged sentinels for other panes; history and last-command callbacks can resolve targets differently. Do not select each calling pane merely to make a missing explicit target pass. If a protected callback needs a correction, obtain the narrow body-change exception before editing, then adjust only its approved baseline-comparison sites. Test boot with no server, an existing server, an empty restore and a successful restore, including the actual confirmation alias so bootstrap leaks are detectable. Mock restore scripts help cover branches but do not establish plugin save/restore correctness. Use only permitted source inputs and obtain access or installation authority before acquiring excluded dependencies. When installed plugin access is excluded, offer scratch-only copies of the already-declared plugins as a separate selectable verification-input permission; this grants neither production dependency changes nor binary installation. Read the parent installer or lock's declared pins before acquiring fixture sources; current upstream HEAD is not interchangeable with the configured release. Record repository URLs, full commit IDs and clean state, and update the input manifest whenever the test checkout changes revision. Copy approved inputs into the test-owned HOME rather than symlinking an installed or shared checkout that a plugin manager could update. Inspect initialization/update behavior and subprocess routing before execution, keep sources fixed during the run, and verify input state afterward. Do not claim a native plugin branch works until it actually executes; an opt-in branch skipped for missing input is still an unmet gate when real persistence is required.
6. Verify service ownership in an already-authorized isolated service-manager environment, or retain a precise coverage gap. Static unit assertions and direct boot execution cannot prove Type=forking behavior, main PID, cgroup membership, boot startup or logout survival. Pair clean service-owned startup with an existing unmanaged server and inspect actual unit/process state. Explain lifetime using the tested logind, user-manager and linger policy rather than asserting every session-scoped process necessarily dies on logout. Do not obtain privileged sandbox access, enable lingering or manipulate host services merely to complete verification; request the exact missing capability when necessary. Inspect available runtimes and namespace/cgroup configuration read-only before proposing access. Separate plan approval, image build/package downloads and capability-bearing launch; plugin-source permission grants none of the others. Present immutable image identity, exact capabilities/security profiles, namespace/mount/network limits, guest-only lifecycle tests, evidence export and verified cleanup. Explain the shared-kernel risk of containers. Keep unexecuted remount/delegation assumptions as feasibility gates; stop rather than widening privileges on failure. Prove PAM/logind session closure rather than treating shell exit as logout; distinguish container startup from hardware boot. Unanswered access choices and required lifecycle gaps remain blocking despite native-test success or reviewer wording. Keep simulated macOS/configuration checks distinct from native platform evidence.
7. When verification uncovers production defects, separate the measured failures from the proposed repair and obtain a bounded owner decision before dispatch. Name the affected files/behaviors, retained feature, alternative and safety tests; preserve unrelated callback bodies and user-facing confirmation behavior. Record approval in the authoritative umbrella/child contract and read it back before admitting implementation. Approval for a code correction does not waive an outstanding service-manager test or authorize deployment. Write maintenance runbooks with an explicit downtime/backup/rollback gate: serialized layouts/history do not preserve arbitrary running processes, unsaved buffers or work since the snapshot. Keep disruptive teardown for a separately confirmed owner operation, and use the verified restore invocation in rollback instructions too.

### Verify agent installation and discovery research

1. Establish the exact integration revision and permitted inspection roots. Find the maintained-agent registry or supported enumeration interface and record its provenance. Treat old split plans, architecture diagrams and selected upgrade commands as leads, not a complete inventory. Mark coverage unknown when evidence is missing; absence from one document does not establish that an agent is unsupported.
2. Trace installation ownership through the parent source, existing registration hooks and permitted secondary-source interfaces before proposing changes. Do not inspect an installed runtime copy to bypass a submodule exclusion. If the required registry or mechanism is outside allowed scope, ask for narrow read-only inspection or an explicit outcome reduction; neither grants edits, gitlink updates, dispatch of parked work or creation of new tasks.
3. Verify the actual supported version and configuration destination against current official documentation or permitted implementation evidence. An existing script writing a plausible JSON file does not prove that the client reads it. For marketplace/plugin systems, distinguish declarative settings from installation records and caches; do not reconcile an ineffective destination merely because the current code already uses it.
4. Build the matrix around separate evidence gates: configuration declared, artifacts installed, client discovery, and loading/activation. Identify the installation owner and exact missing gate for each maintained agent. Creating an empty skills directory is preparation, not skill delivery. A proposed dependency on excluded source is unresolved scope, not permission to defer required functionality or claim completion.
5. Reuse the existing distribution mechanism and test it with isolated HOME/XDG, fake commands and canaries before proposing another installer. Keep synthetic file/schema tests distinct from native discovery evidence; request authority before real client startup or host configuration mutation. Preserve user-disabled entries and unrelated settings. Do not claim JSON reserialization preserves formatting or that atomic replacement alone preserves file modes, symlink boundaries or concurrent edits; test whichever guarantees the approved implementation actually requires.
6. Return a focused correction when a report guesses agent coverage, current mounts or native enablement. Carry the corrected scope and evidence gaps into worker instructions, then resolve any genuine access/ownership decision before implementation. Do not accept `SCOPE: SINGLE_TASK` as permission to drop agents, add duplicate setup paths or change excluded sources.

### Verify Git-metadata enforcement before accepting a design

1. Enumerate direct metadata, pointer files, ancestors, missing entries, and existing hook/config indirection at the inspected revision. Separate protected-at-launch resources from metadata created later. Do not describe a later protected launch as sanitizing commands or hooks planted previously.
2. Build only synthetic repositories under the configured scratch directory. Isolate Git from real HOME/global/system configuration and credentials. First reproduce the claimed bypass with a negative-control mount layout, then test the proposed correction; require actual exit statuses and unchanged sentinel bytes rather than policy-argument snapshots.
3. On Linux, test writable repository bind plus read-only child mounts by attempting `mv .git .git.moved` and replacement metadata creation. Child mounts alone do not prevent renaming their unmounted ancestor. Test an additional read-write self-bind of the metadata root before its read-only child overlays; the root itself is then a mountpoint. A synthetic normal-repository probe verified rename denial, config-update denial, and successful staging, commit and branch creation with this ordering. Re-test actual supported runtimes and path shapes; this result does not certify linked worktrees, bare repositories, races or macOS. On a path-policy backend, a read-write bind does not itself imply mountpoint-style root integrity. Trace what actually emits the root denial: if pins are derived only from read-only children, omitting those children in relaxed or absent-entry modes can remove the mandatory protection. Probe root rename/replacement separately in protected, relaxed and absent-entry layouts, alongside successful persistent Git writes; do not extrapolate the protected-mode result.
4. Validate every discovered Git path before running hostile probes: require successful `git rev-parse`, nonempty canonical paths, expected fixture membership and valid pointer relationships. Abort on discovery failure rather than constructing paths from empty values. Check the probe process status as well as its markers, and include a negative control proving failed discovery cannot produce a passing denial test. `rm -f` on an absent wrong path can report success without touching the intended resource. Test writes, truncation, atomic replacement, deletion/recreation and symlink/hardlink aliases, alongside ordinary index/object/ref updates. For an atomic-rename assertion, invoke `rename(2)` directly through an available runtime; `mv` may fall back to copying and deleting across mount boundaries. Distinguish denied final rename from inability to create a sibling lock file. Treat `git push -u` as potentially partial: remote publication can precede failure to write local tracking configuration.
5. Handle absent hooks/config entries explicitly. Skipping a nonexistent path leaves a creation bypass; creating it mutates host state and needs authorization and safe creation semantics. A requirement to keep launch available grants neither host-write permission nor acceptance of that bypass. Do not mask the Git executable as proof that metadata cannot be created: arbitrary code can write the files directly.
6. Freeze direct config and hooks only within the approved boundary. Existing includes, hooksPath, filters and command targets can reference writable content; unchanged configuration does not make those targets immutable or establish prior owner trust. Record accepted residuals and warn about detected indirection without claiming exhaustive detection or complete host-execution prevention.
7. Require native platform enforcement tests. If a backend prerequisite is missing, propose moving its sibling earlier or an explicit staged-acceptance boundary. After owner approval, update the umbrella's authoritative order, local cursor and affected worker handoffs before dispatch; do not leave contradictory ordering in the body and comments. Preserve canonical sibling ownership rather than silently implementing the prerequisite inside the current task.
8. Inspect backend parser state, extension callbacks, extra-directory settings and base-profile grants before choosing an overlay representation. Preserve supported callback arrays and mutations even when consolidating internal storage. Test read-write parent, read-only container, writable selected child and read-only pointer files, plus reversed/duplicate inputs and metadata-only traversal. Treat Seatbelt precedence, operation names and ancestor-denial behavior as hypotheses until real `sandbox-exec` tests establish both denial and legitimate writes. Generated policies and Linux mocks cannot certify these semantics. Broad ancestor denials require positive traversal/create/Git controls; many denied hostile probes can merely mean the entire workspace is unusable. Test a synthetic HOME nested below the normal user-home location: Git canonicalization may need metadata-only access to intermediate HOME ancestors. Distinguish missing traversal grants from write-pin failures with a focused native stat/list/create/rename probe before changing deny scope. Keep traversal grants literal and metadata-only rather than opening ancestor contents or writes.
9. Finish synthetic fixture preparation before capturing protected-state baselines, including any optional hook directories the launcher normally prepares. Require snapshot commands to succeed and compare exact protected paths and bytes after execution. If the snapshot changes, distinguish authorized fixture preparation from hostile mutation; do not drop the preservation assertion or exclude the changed resource to obtain green CI. Ensure mandatory native steps actually ran: a failed earlier step can prevent later certification tests from executing.
10. Before recursive module discovery, enumerate every existing walker and writable root: local/bare metadata, external shared metadata, and the selected worktree entry can have separate bind plans. Generate real nested and slash-name submodule fixtures to distinguish Git directories from namespace parents. Do not require an optional config file as the sole classifier: a synthetic repository remained discoverable by `git rev-parse --absolute-git-dir` after its config was removed. Validate symlink/type markers before using them, retain approved missing-entry warnings, and avoid traversing object/ref storage as if it were a namespace. Do not describe an untested classifier or incomplete research proposal as verified.
11. Extend replacement probes to every writable namespace ancestor, not only module leaves. A self-bound leaf does not make an unmounted ancestor immovable on Linux; moving that ancestor can carry its child mounts away and expose replacement paths. Test module roots, slash-name namespace parents and their containing `modules` directories with native rename/move-and-back/recreation probes. Apply any required parent pins before descendant pins and read-only overlays, because a later parent read-write mount can hide earlier child protection. Recheck relaxed and absent-entry modes independently and confirm ordinary Git writes persist. Preserve logical/canonical alias coverage and native macOS verification rather than extrapolating mount semantics to path rules.
12. Resolve recursive policy before implementation: ask whether an existing config/hooks control expresses the same boundary, and state separately which external shared resources remain unconditionally read-only. Carry final menu/preset values into setting-dependent active-worktree protection; do not freeze them in an early shared-dir binder. Inspect every caller's handling of discovery/type/limit failures so an ignored return cannot be followed by writable exposure. Present proposed depth/module caps as compatibility decisions, not measured safe defaults; obtain approval, define counting across namespace levels and multiple roots, and test the exact boundary and overflow. Never silently leave an unprotected tail or expand host-side directory creation merely because the old shallow walker performed it.

### Verify namespace preflight and terminal protection

1. Record the real wrapper command, current procfs knobs, callback/filter inputs and selected policy values. Treat an absent knob as inconclusive, an explicitly disabled value according to the approved refusal policy, and unreadable or malformed input as an error to handle. Inspect actual runtime behavior rather than assigning kernel features by distribution name. Check flag support through successful capability inspection and execution; do not silently warn-and-omit requested enforcement on an older binary.
2. Establish an execution baseline before diagnosing namespace failure. Resolve an absolute external executable with `type -P true` or an explicitly checked executable path; `command -v true` can return the shell builtin token. Include the executable's ELF interpreter and available library paths. A useful native probe layout is `bwrap --unshare-user --ro-bind /usr /usr`, followed by read-only binds for each existing `/bin`, `/lib` and `/lib64`, then the checked absolute executable. Adapt this to the supported runtime rather than assuming every host has that layout. Capture status and stderr in memory. Pair a capable baseline with namespace-denied and missing-loader controls; `execvp ... No such file or directory` does not establish a user-namespace restriction. Keep sensitive host paths out of probe mounts and avoid fixed temporary error files.
3. Exercise nested namespace enforcement and its explicit relaxation separately. Require a successful outer sandbox, denied nested creation in protected mode, successful nested creation in relaxed mode where the baseline permits it, and ordinary CLI/Git controls. Distinguish clients using an already-authorized host daemon socket from daemons or browsers creating namespaces inside the sandbox; successful client communication does not certify all container or browser workflows.
4. Create an isolated PTY with `pty.fork()` or an equivalent harness and execute the real bubblewrap command inside its child session. Never inject test input into the owner's terminal. Run baseline and protected variants with the same mount layout and payload. Check `/dev/tty`, terminal attributes, raw input and window-size queries, then install payload handlers and emit a readiness marker. Drive resizing with `TIOCSWINSZ` on the master and Ctrl+C with `os.write(master, b'\x03')`; require receipt markers and bounded cleanup of only that isolated child/process group. Use explicit readiness/acknowledgment stages so resize and interrupt do not race handler installation or each other. Record payload cancellation separately from the outer `waitpid` status: a child can print its clean-cancellation marker while bubblewrap itself terminates from SIGINT. Compare baseline behavior instead of changing a status assertion merely to obtain a pass.
5. Measure injection errors against the same kernel baseline. If unfiltered `TIOCSTI` already returns `EIO`, a protected denial alone proves nothing. A targeted filter returning its configured `EPERM` while ordinary terminal operations still work establishes filter activation on that tested host, not successful injection on permissive kernels or universal ABI coverage. Keep `TIOCSCTTY`, `TIOCSTI` and `TIOCLINUX` findings separate; failure to acquire a controlling terminal is not a direct test of every injection request. Do not infer real-client TUI compatibility from termios calls alone, or infer actual bubblewrap signal forwarding from a `setsid()` simulation.
6. Compare the smallest feasible mechanisms before asking for architecture approval. For controlling-terminal preservation, evaluate runtime libseccomp generation before asserting that seccomp requires committed binary blobs or handwritten syscall tables. Where approved and available, resolve the native `ioctl` syscall with `seccomp_syscall_resolve_name`, add scoped argument comparisons, export BPF with `seccomp_export_bpf` to an anonymous descriptor such as `os.memfd_create`, rewind it, and explicitly arrange inheritance into bubblewrap. Declare ctypes argument/result types and check every API status. Account for the kernel's ioctl request width, including high-bit aliases, and test native/available compatibility ABIs and architecture-mismatch handling. This is a mechanism to validate, not a portable implementation certified by one successful host probe.
7. Obtain approval for interpreter/library prerequisites and behavioral trade-offs before implementation. In hardened mode, missing Python/library symbols, unsupported architecture, filter-generation/export errors, descriptor inheritance failure and filter-load failure must refuse launch with actionable guidance. Preserve existing caller traps, plugin filter arguments and process cleanup; do not introduce signal-forwarding or a PTY supervisor merely to conceal unmeasured `--new-session` regressions. Require actual-wrapper native PTY and negative dependency/descriptor tests at the final head, with CI evidence kept separate from the parent feasibility probe.

### Verify runtime-directory and socket isolation

1. Trace the complete native mount and environment plan at the inspected SHA: `/run` and `/tmp` tmpfs layers, WORKDIR, explicit extra binds, named service sockets, `--clearenv`, subsequent `--setenv`, and extension callbacks. A variable set before `--clearenv` is not exported to the final child; inspect the child environment as well as argument order.
2. Prove the private runtime directory's mode and ownership in a minimal native sandbox. Bubblewrap `--dir` alone can yield `0755`; use `--perms 0700 --dir "$runtime"` when creating a private runtime directory and verify with `stat -c '%a:%u' "$XDG_RUNTIME_DIR"`. For shell helpers producing identities, paths or access-validation results, check the producer's status before passing its output to `printf`, `dirname`, extraction tools, deletion commands or `[[ -n ... ]]` / `[[ -z ... ]]`; a successful consumer or string test can mask a failed substitution. In particular, empty output from a failed permission scan must not authorize a bind. Validate the complete digest or identifier before truncation, including valid-looking output from a command that exits nonzero. Resolve all required paths before the first filesystem mutation. Use independent expected values and no-mutation canaries; test-only dependency shims and expected values computed with the same broken pipeline can hide production failures. For `grep`/`git grep` absence assertions, distinguish exit 0 (matches), 1 (no matches), and operational errors; empty stdout after an error must fail. Test match, no-match and forced-error controls, including missing Git metadata when the test depends on a checkout. Validate the widget/client process status independently of its output: failed execution returning empty stdout is not a clean result. Check fixture creation and command resolution before use, and restrict cleanup to validated test-created paths.

### Reconcile security residuals and usability before merging

1. Maintain one owner-decision register across the milestone (`Resource -> protected default -> explicit override -> persistence -> mandatory invariants -> accepted residual`) and compare it against the current PR head, implementation notes and security documentation. Before retiring a feature, inventory its runtime mounts, settings, environment variables, installers (including mixed-purpose installers), hooks, documentation, tests, and host data. Treat an automated `APPROVED` signal as review evidence, not authority to waive a contradictory acceptance criterion.
2. Trace effects before detection. For libraries that reopen files by path, inspect database sidecars and parent traversal as well as the main descriptor. A check after a query or write can report an escape after damage occurred. Require deterministic swap canaries proving external sentinel bytes remain unchanged. If safety depends on library or filesystem behavior, verify the actual supported runtime and fail closed when the required property is absent; do not extrapolate one probe to every race or platform.
3. Separate atomic replacement, cooperative serialization and protection from non-cooperating writers. Inject a competing write at the exact final-check/rename boundary. Advisory directory locks coordinate wrappers that take the same lock; editors or clients ignoring it can still lose updates. Process-presence checks and fewer writes reduce exposure but do not eliminate that window. Offer a precise residual acceptance, a concrete read-only workflow, or a design change; do not quietly certify compare-and-swap semantics.
4. Enumerate the complete effective write plan before trusting an approval stored on the host. Include late plugin hooks and configurable binds. Refuse the approval when later mutation of that plan makes its protection unknowable, rather than assuming the preset remains outside writable roots. Keep this check tied to the trust exception instead of building a second general sandbox policy engine.
5. Present read-only changes as an operation table before implementation. Read-only settings validation must not create missing files/directories, change permissions, or replace symlinks; missing configuration needs specific setup and retry guidance. State whether the restriction applies only to wrapper host operations or also to the launched client. Do not infer either scope from the other.
6. Preserve requested session-management usability independently of settings policy. Keep rename available when required, validate before avoidable partial changes, and propagate persistence failures with actionable diagnostics and nonzero status. Test the displayed title, not only the database field: a title-override file can mask a nominally successful database-only rename. Retain meaningful lock, permission and detected-conflict tests. Describe undetected races honestly; a diagnostic requirement is not proof that every collision is observable.
7. Record the chosen trade-off and superseded proposal in the authorized handoff before restarting the existing loop. Distinguish accepting a title-writer limitation from accepting settings writes or unrelated security gaps. Require fresh current-head tests/review after behavior changes, then verify the implementation against the revised contract before the normal merge gate.

### Retrigger CI after an infrastructure failure

1. Read the exact PR head, current-head review metadata, check conclusions, and failed job logs (`gh run view RUN_ID --log-failed --repo OWNER/REPO`). Distinguish a test failure from setup/build failure before tests started. An approved review with unresolved infrastructure questions does not authorize merging a red required check.
2. Obtain action-specific rerun authority. Prefer `gh run rerun RUN_ID --failed --repo OWNER/REPO` over code changes or storage cleanup. Capture a fresh `make -s get-github-token REPO=OWNER/REPO` inside the process and pass it through `GH_TOKEN`; retry once with the fresh token if the first attempt failed. Read back `attempt,status,conclusion,headSha`. A fresh-token permission denial is not evidence of expiry, and an unchanged attempt is not an active rerun.
3. Do not prune Docker storage, restart the runner, change workflow permissions, or obtain broader credentials as a side effect. Each needs separate authorization. A build snapshot error identifies the failed stage, not a proven safe cleanup procedure.
4. If direct rerun remains unavailable, offer a separately authorized empty-commit fallback or an owner-triggered rerun. Explain that an empty commit retriggers all applicable checks and invalidates the old head-scoped review. Do not present it as rerunning only the failed job.
5. Under fallback authorization, re-read the remote head and active runs before writing. Fetch the exact branch into an isolated checkout while preserving unrelated local changes. Create only an empty commit (`git commit --allow-empty -m 'test: retrigger CI after infrastructure failure'`); assert its parent is the observed head and its tree equals the parent's tree. Re-read the remote head immediately before a normal fast-forward push; abort and reconcile if it changed. Never force-push to overcome this race or persist credentials in remote URLs.
6. If another actor already published a retrigger, inspect its parent, tree, changed-file count, and new workflow run instead of adding another commit. Verify unchanged content and the actual remote head without claiming authorship from a matching commit message. A local assertion or failed command can occur after partial side effects; reconcile before retrying.
7. Verify the new PR head and newly created checks, then resume PR-scoped monitoring with renewable credentials. If the immediate PR read still reports the old head, reconcile the exact remote branch and retry bounded readback before declaring publication failed or creating another commit; GitHub's PR view can lag a successful push. A rerun of the same SHA can preserve code-review identity; an empty commit needs a fresh review tied to its new SHA even when the code tree matches. Resolve the review's infrastructure question from verified successful checks, post only owner-actionable context when authorized, and require the normal green-current-head merge gate.
8. Carry a retry-only owner decision into the PR before an automatic correction cycle consumes a broader review suggestion. State the published retrigger SHA, unchanged-tree proof, forbidden lifecycle/test/resource changes and remaining CI/review gate. Reconcile any concurrently admitted successor; do not add a duplicate trigger or interpret its existence as authorization to expand scope. Retry authorization does not authorize a proposed production fix or follow-up issue.

### Recover pushed commits without a pull request

1. Read the exact remote child head and intended integration base, then search open PRs by head branch and issue-closing marker. Treat `completed` with `nothing_to_push` as an execution outcome, not proof of publication; a retry can inherit already-pushed commits and skip PR creation because it made no new commit.
2. For a publication error naming an invalid base, read every required ancestor integration ref before retrying. Under branch-publication authority, create only missing prerequisite refs from their verified intended parent SHA and read them back. Never overwrite existing refs or redirect the child to the default branch to bypass routing.
3. Preserve the published commits and original verification evidence. If no worker or retry owns publication and PR creation is authorized, open the draft PR directly against the intended base; do not dispatch another full implementation solely to reproduce an already-known publication failure. State exact commands, tested SHA, and verification limits in its body rather than relabeling a unit-only result as the full suite.
4. If implementation stopped for an unapproved lint exception, inspect the exact source statement and bootstrap/caller constraints before asking. Record any approved exception at statement scope, then resume the existing branch; a new necessary fix may justify implementation, but an empty commit is not a publication repair.
5. Verify the actual PR head and base after recovery, then enter the authorized review loop and require current-head checks. Correcting refs or scheduling a retry alone does not prove PR recovery.

For failed pushes with no remote branch, establish whether exact code survived before choosing publication recovery or reimplementation:

1. Read the run's verification artifact for `tested_commit`, `final_head`, suite target and push result. Resolve its recorded worktree and check that it still exists; retries and cleanup can remove it even while logs remain.
2. Test exact object availability with `git -C CHECKOUT cat-file -t SHA` in the retained checkout or known shared clone. Read the exact remote branch and, when needed, `gh api repos/OWNER/REPO/git/commits/SHA`; a missing branch alone does not establish object loss. Distinguish authenticated not-found responses from access or transport failures. Check known exported patches or bundles without scanning credential directories or dumping all repository refs.
3. If exact commits or complete patches survive, export them before another cleanup/retry and use authorized owner-side publication. If none survive, state that recovery failed; logs, summaries and successful verification metadata cannot recreate a commit.
4. Reconcile active runs and the retry queue again. If no successor owns execution and implementation remains authorized, retrigger once on the unchanged approved route with the prior findings clearly labeled as historical context. Require all checks anew on the replacement head; never call regenerated changes recovered commits.

Before adding review/loop labels after publication, re-read PR labels and matching bridge evidence: implementation completion can transfer the loop concurrently. Leave an admitted automatic review in control rather than adding a duplicate trigger. If a multi-write command fails an assertion, read back every preceding write before retrying; metadata edits may have succeeded even though a later label precondition became stale. Under authorized PR edits, remove progress chatter and internal task handles from the body, retain substantive evidence, and correct unit-only targets mislabeled as full-suite verification without altering the tested SHA or result.

### Diagnose provider limits and arrange authorized resumption

1. Reconcile the exact issue, open PRs, `/admin/runs`, and `/admin/queue` before changing labels. Filter run records by `repo_full_name`, issue or PR number, and task type; issue numbers alone collide across repositories. Record the intended retry ID from bridge evidence rather than repeatedly selecting the old failed run.
2. Inspect the failure stage before retrying. Read the run-scoped `${LOGS_DIR}/${RUN_ID}.verification.json`, then its `.exit_reason` when present. If the reason is missing or only says `initial_session_failed`, inspect a bounded, credential-safe excerpt of `${LOGS_DIR}/${RUN_ID}.log`. An exited runner container may already be removed while these shared log files remain. Never dump credentials, full environments, or unrelated run logs.
3. Separate provider admission failures from code and suite failures. A session/quota limit with `suite_result=skipped` and no tested commit is not a failed regression test. Report the provider's reset statement with its timezone, without treating an estimated reset as proof that capacity has returned. Compare the exact raw message against the deployed classifier and inspect matching pause/probe state before promising canary recovery; an unrecognized quota message can exhaust ordinary retries without activating that recovery path. Use the operations skill's classification diagnostic rather than treating missing pause keys or the owner's restoration notice as proof that the task resumed. If the message is unrecognized, verify all three recovery gates independently: matching provider pause/probe state, an admitted task successor or queued retry, and actual publication. When the classifier misses the message, recovery state is absent and retries are exhausted, name the recovery-path fault explicitly. A read-only watcher can preserve notification continuity but cannot discover restored capacity from unchanged terminal run records. Record that evidence limit and the next authorized recovery condition in the cursor; do not present periodic observer renewal as repaired automatic continuation. Do not manufacture reset-time jobs, repeat implementation triggers to probe quota, or modify infrastructure under task-only authority.
4. Leave admitted automatic retries with Tortuga. Do not re-add labels while a retry is queued or running, and do not treat a temporarily absent retry record as exhaustion. On each terminal notification, reconcile whether another retry was scheduled. Preserve partial work and existing commits even when no PR was published.
5. Treat waiting on the unchanged configured route and continuing authorized work after restoration as standing owner policy. Do not ask permission merely to wait or resume. Keep observation active through provider pauses and let Tortuga's built-in canary refresh limits and own recovery. Change model, effort, provider, account, quotas, or batch scope only with separate explicit authorization.
6. Reconcile provider pause/canary evidence with queued retries, run status and the exact PR before classifying a terminal attempt. A failed attempt, exhausted short retries, or temporarily absent replacement record does not prove built-in quota recovery has stopped. Preserve the recovery owner's identity; do not manually relabel, alter queue schedules, create reset-time jobs, or install another recovery scheduler as a substitute for the canary. Keep a bounded observer alive across failed/queued replacement runs and renew observation at its budget boundary without another wait approval. Report only meaningful state transitions.
7. When the canary reports restored capacity, check whether the task was actually readmitted on the unchanged approved route; provider recovery and task recovery are separate events. If retry exhaustion deactivated the coordinator and no successor exists, read the exact issue/PR, matching runs and retry queue again. Search existing publication and preserve recoverable partial work. Within existing comment/label authority, record the verified recovery, re-add the implementation/loop trigger once, read it back, and require bridge admission before claiming execution resumed. Do not ask for another start instruction or change the model/account. Leave queued/running successors with their existing recovery owner; label absence alone is not proof of abandonment. Renew observation and retain normal current-head CI/review and final acceptance gates. Investigate other recovery faults or misclassified provider failures without installing a competing scheduler.

### Recover a publish-blocked dependency fix

When a restricted implementation runner produces valid dependency commits but cannot push:

1. Stop cycling the unchanged parent; another review cannot inspect unpublished objects.
2. Recover exact commits from the retained worktree when available. Otherwise extract the complete `git format-patch` block from the implementation comment and verify its digest before applying it.
3. Fast-forward the local dependency branch to the published PR head, apply the recovered commits with `git am`, and run the dependency's full verification plus focused regressions.
4. Under existing user authorization, publish with the repository-scoped App token from the owner-side session. Read back the remote branch SHA; never rewrite remotes with a persistent token.
5. Repin the parent only after the dependency SHA is remotely fetchable. Commit and publish the parent, then verify its remote head and exact gitlink.
6. With explicit authorization for PR comments and review labels, comment the resolved SHAs and verification on the parent PR, then request a fresh dependency review; after its latest head is approved, request or accept the parent review.

Do not grant the runner broader push permission as a shortcut. Preserve the security boundary and use the already authorized owner-side publication path.

## 5. Child approval, stale-loop and merge gate

This section applies to child PRs and nested integration PRs only when their merge is covered by the user's explicit batch authorization. It does not authorize merging the umbrella's final integration PR.

Before merging, read the exact PR and verify:

1. current head SHA;
2. latest-head checks, not checks from an earlier revision;
3. latest review result and unresolved change requests;
4. open questions or failed verification comments;
5. intended base branch, especially for integration-branch children;
6. implementation notes and documented residuals against the latest owner-approved contract. Green CI and automated approval do not override an in-scope security violation or an unapproved usability regression;
7. independent targeted results at that exact head, separated from runner results and skipped orchestration. Supply only an already-authorized exact pinned dependency checkout when a regression's input is absent; do not initialize or inspect excluded dependencies implicitly. Recount results from execution instead of copying runner totals, because available runtimes can change which assertions run;
8. remaining claims at scenario granularity. A successful Zsh namespace probe does not prove Ctrl+D keystrokes, completion interaction or full shell parity; use isolated PTYs for interactive claims and distinguish simulated platform layouts from native evidence. Record baseline defects under their canonical task rather than counting characterization as repair.

If the loop approved, merge under the user's standing authorization. If the loop merely went stale, merge only when that stale-loop behavior was explicitly authorized and the checks above show no material blocker.

Before choosing `--merge`, `--squash`, or `--rebase`, query the repository's enabled merge methods; do not assume the default. Check unresolved review threads, paginating when necessary. Mark an approved draft ready before merging when required and verify draft status changed. Bind the merge to the reviewed SHA with `pr merge PR_NUMBER --match-head-commit HEAD_SHA` plus the enabled merge method, so a concurrent push cannot bypass the checked gate. A successful merge command is not enough: read the PR and child back afterward, require visible merged/closed state, and record the actual integration merge SHA before advancing. A child PR merged into a non-default integration branch may leave its closing-linked issue open. If explicit issue-closure authority exists, close that completed child with the merge and verification evidence, then read back its closed state; otherwise request only that missing mutation authority. Verify the integration ref at the actual merge SHA, pass it to the next authorized child's handoff, and verify admission and loop activation before reporting that the batch advanced.

## 6. Prepare the final integration PR for acceptance

After every child is closed and no child PR remains open:

1. fetch the integration branch and confirm the preserved dirty files do not conflict with its remote changes;
2. switch to the integration branch without discarding the initial dirty configuration;
3. inspect the configuration diff and ensure it belongs to the umbrella outcome;
4. trace every changed default through the typed/schema fallback, runtime documentation, and hard-coded default tests. Update those copies together; changing only the loaded YAML can make alternate config paths disagree;
5. preserve model selectors exactly as configured, including any `@effort` suffix, unless the code you inspected explicitly strips it;
6. run focused configuration tests and the repository's full verification. Start long image-based suites as tracked background jobs with completion notification so a client call deadline does not orphan the test container or lose its final output;
7. commit only the intended, verified diff; push/update the integration PR only when branch publication was explicitly authorized;
8. read back the remote branch/head and verify BOTH all latest-head CI checks are green AND a current-head review comment containing `<!-- AGENT_LOOP_META {"signal": "APPROVED", ...} -->` is present;
9. stop and give the user the PR URL, exact head, verification results, unresolved risks, and a self-contained manual acceptance checklist (exact revision, reproducible setup, actions, expected results, known exceptions, sign-off boundary). Do not deploy unless explicitly requested;
10. wait for explicit approval to merge that exact integration PR. Child-merge authorization, loop approval, stale-loop authorization, and umbrella-completion intent are not approval for this merge;
11. after approval, merge using the repository's enabled method, then read back the umbrella and integration PR to confirm closure.
